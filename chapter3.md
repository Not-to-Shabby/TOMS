# **3.4 System Design and Architecture**

&emsp;&emsp;&emsp;This section describes the methodology used to derive the system's hardware topology, inter-device communication protocol, and security architecture from the functional and non-functional requirements identified in Chapter II.

## **3.4.1 Overall System Topology**

&emsp;&emsp;&emsp;(T) The system topology defines how the physical devices are organized and how data flows between them during a boarding transaction. (R) For this project, the topology must satisfy three constraints derived from the requirements analysis: (1) the Slave terminal must remain a passive, low-cost display device that never stores transaction history; (2) the Master handheld must operate as the single source of truth for fare logic and event logging; and (3) the mobile phone must serve as the cloud gateway without being required for offline operation. (I) A three-tier Master-Slave-Phone hierarchy is adopted. The Slave communicates with the Master via two independent channels: a contactless NFC-DEP (ISO 18092) Peer-to-Peer link for tap-based boarding commands, and an ESP-NOW 2.4 GHz radio link for wireless confirmation and heartbeat messages. The Master bridges the embedded hardware to the Flutter mobile application through a USB On-The-Go (OTG) connection using the CDC-ACM virtual serial protocol. This separation ensures that a Slave failure does not affect the Master's ability to continue logging events, and the absence of a phone does not prevent the Master from recording transactions locally.

## **3.4.2 NFC-DEP Peer-to-Peer Communication Interface Design**

&emsp;&emsp;&emsp;(T) The NFC-DEP interface replaces the legacy pogo-pin UART docking mechanism with a contactless Peer-to-Peer data exchange, eliminating mechanical wear and enabling a faster tap-and-go user experience. (R) For this design, the PN532 NFC transceiver is selected as the common hardware module for both Master and Slave, operating exclusively in NFC-DEP passive mode at 424 kbps over an I2C bus clocked at 400 kHz. The Master is configured as the permanent Initiator (calling `pn532_in_jump_for_dep`), while the Slave is the permanent Target (blocking on `pn532_tg_init_as_target`). (I) To minimize latency on the bandwidth-constrained NFC link, a dictionary-based compression strategy is employed: instead of transmitting the full 40-byte `toms_board_command_t` structure, the Master sends a compact 6-byte `toms_nfc_board_cmd_t` packet containing only a 1-byte fare dictionary index (`fare_id`), a 1-byte seat assignment, and a 4-byte UTC epoch timestamp. The Slave expands the `fare_id` into the full fare and route information using a locally cached fare dictionary that is synchronized during the initial ESP-NOW pairing handshake. The Slave responds with a 1-byte `toms_nfc_ack_t` containing a status code (`TOMS_NFC_ACK_OK`, `TOMS_NFC_ACK_FAIL`, or `TOMS_NFC_ACK_BUSY`). Slave identification is implicit: the first 6 bytes of the Slave's 10-byte NFCID3 (extracted during the `InJumpForDEP` handshake) correspond to its eFuse MAC address, uniquely identifying the terminal without a separate UID exchange.

## **3.4.3 Unified Communication Protocol Design**

&emsp;&emsp;&emsp;(T) A single, unified packet format is used across all physical channels (NFC-DEP, ESP-NOW, and USB CDC-ACM) to guarantee format consistency and simplify both firmware and debugging. (R) For this implementation, the protocol is defined in a shared C library (`protocol.h`) that is compiled identically into both the Master and Slave firmware projects via a symbolic link, eliminating the possibility of format mismatch between devices. (I) The on-wire packet layout (`toms_packet_t`) consists of a 2-byte synchronization word (`0xAA55`), a 1-byte payload length field (0–240), a 1-byte message type field (`toms_msg_type_t`), a 1-byte monotonic sequence number, a variable-length payload, and a 2-byte CRC-16-CCITT checksum computed by `toms_crc16()`, producing a fixed overhead of 7 bytes (`TOMS_PACKET_OVERHEAD`). Message types are categorized by direction: Slave-to-Master messages occupy the range `0x01–0x0F` (including `PASSENGER_BOARD`, `BUTTON_PRESS`, and `UID_RESPONSE`), Master-to-Slave messages occupy `0x10–0x1F` (including `CONFIG_SYNC`, `BOARD_COMMAND`, and `NFC_BOARD_CMD`), acknowledgments occupy `0x20–0x2F` (including `NFC_ACK`), and utility messages occupy `0xF0–0xFF` (including `HEARTBEAT`).

## **3.4.4 Anti-Fraud Security Architecture Design**

&emsp;&emsp;&emsp;(T) The security architecture is designed to prevent unauthorized boarding commands and protect transaction data from interception or tampering. (R) For this project, a dual-layer approach is adopted: a hardware-level device authentication layer and a link-layer encryption layer, with an optional application-layer encryption layer available for sensitive payload fields. (I) The first layer uses UID-based validation: in the ESP-NOW path, every `BOARD_COMMAND` packet contains a 16-byte `target_uid` field that must exactly match the receiving Slave's eFuse MAC address (zero-padded to 16 bytes); mismatches cause the packet to be silently dropped. In the NFC path, authentication is implicit because the Slave's NFCID3 (containing its eFuse MAC) was already captured during the `InJumpForDEP` handshake. The second layer is ESP-NOW's native CCMP (AES-128) encryption applied to all wireless frames using a 16-byte Local Master Key (`s_espnow_lmk`) shared between paired devices. The optional third layer is application-level AES-256-CBC encryption via the mbedTLS library (`toms_crypto_init`), with the 256-bit key stored in Non-Volatile Storage (NVS).

# **3.5 System Development**

&emsp;&emsp;&emsp;This section describes the methodology used to implement the firmware, real-time task scheduling, offline storage mechanism, and mobile application integration during the prototype build phase.

## **3.5.1 Master Firmware Development Methodology**

&emsp;&emsp;&emsp;(T) The Master firmware is the most complex component of the TOMS system, orchestrating all inter-device communication, fare logic, event storage, and phone integration. (R) For this project, the firmware is built on the Espressif ESP-IDF 5.5.3 framework, targeting the ESP32-S3's dual-core Xtensa LX7 processor. The development methodology follows a modular, compile-and-flash iterative cycle using `idf.py build` and `idf.py flash monitor` over a USB-JTAG debug interface. (I) The Master firmware is organized into six independent modules, each encapsulated in a dedicated header and source file within the `main/` directory: (1) `toms_espnow.h` for ESP-NOW wireless communication, (2) `toms_usb_cdc.h` for USB CDC-ACM phone I/O, (3) `toms_nfc_sync.h` for PN532 NFC-DEP Initiator logic, (4) `toms_storage.h` for SPIFFS offline log management, (5) `toms_crypto.h` for AES-256-CBC encryption, and (6) `toms_power.h` for battery ADC monitoring. The initialization sequence in `app_main()` proceeds through eight explicit, ordered steps, and all four runtime FreeRTOS tasks are created with explicit core affinity via `xTaskCreatePinnedToCore` to prevent scheduling interference between latency-sensitive radio tasks and I/O-bound tasks.

## **3.5.2 Slave Firmware Development Methodology**

&emsp;&emsp;&emsp;(T) The Slave firmware is designed as a strictly passive terminal whose sole function is to display boarding information and generate QR receipts on command from the Master. (R) For this project, the Slave firmware is also built on ESP-IDF 5.5.3, sharing the same `protocol.h` library as the Master to guarantee wire-format consistency. The display pipeline uses the LVGL 8.3 graphics library for hardware-accelerated rendering on an ST7735S SPI-connected TFT LCD at 128×160 pixels. (I) The Slave is organized into five modules: (1) the Display Driver interfacing with the ST7735S via SPI2_HOST on GPIO 11 (MOSI), GPIO 12 (SCLK), GPIO 10 (CS), GPIO 9 (DC), GPIO 14 (RST), and GPIO 13 (Backlight PWM); (2) the UI Engine managing six screen states (Welcome, Processing, Fare, QR, Error, and Sleep) with a FreeRTOS mutex protecting all LVGL API calls; (3) the QR Generator producing QR codes from the plaintext receipt string `TOMS,VEH_ID,TIMESTAMP,FARE,UID`; (4) the Button Input module with GPIO interrupt and 50-millisecond software debounce; and (5) the NFC Target listener task running `pn532_tg_init_as_target` in a blocking loop. The Slave firmware excludes all business logic, fare calculation, and storage management modules present in the Master.

## **3.5.3 Dual-Core Task Scheduling Methodology**

&emsp;&emsp;&emsp;(T) The FreeRTOS task model is designed to exploit the ESP32-S3's dual-core architecture by separating latency-sensitive radio operations from I/O-bound processing. (R) For this project, tasks are assigned to specific cores using `xTaskCreatePinnedToCore`, with priority levels chosen to ensure that time-critical radio operations always preempt lower-priority I/O tasks. (I) On the Master, Core 1 is exclusively dedicated to the ESP-NOW handler task (`espnow_handler_task`, priority 6, 4,096-byte stack), which processes incoming wireless packets from a 1-second blocking event queue. Core 0 hosts the USB CDC task (priority 5), the NFC sync polling task (priority 4), and the storage flush task (priority 3). On the Slave, the main logic task and the LVGL timer task share Core 0 with mutex-protected access to LVGL API calls. Task performance is evaluated by instrumenting the firmware with `esp_timer_get_time()` microsecond timestamps at key processing boundaries and logging the results over the serial monitor.

## **3.5.4 SPIFFS Offline Storage Methodology**

&emsp;&emsp;&emsp;(T) The offline-first storage strategy ensures that all boarding events are persistently recorded in the Master's SPI flash memory even when the mobile phone is not attached. (R) For this design, the SPIFFS (SPI Flash File System) partition is used because it provides a flat file namespace with wear-leveling on the ESP32-S3's internal flash, and does not require an external SD card module. (I) Passenger events are serialized into binary log files stored at the SPIFFS mount path `/storage`. Each log file accumulates up to 1,000 records before the system rotates to a new file. Unsynced files carry a `.log` extension; upon successful transfer to the phone via USB CDC, they are renamed to `.done` and eventually deleted to reclaim flash space. The `storage_flush_task` (running on Core 0 at priority 3) periodically wakes to flush any buffered writes. Storage reliability is validated by running a stress test in which the phone is disconnected, a known number of boarding events are triggered, the phone is reconnected, and the event counts in SPIFFS and SQLite are compared.

## **3.5.5 Flutter Mobile Application Development Methodology**

&emsp;&emsp;&emsp;(T) The Flutter mobile application is developed as the cloud gateway and real-time operator dashboard, communicating with the Master ESP32 via USB OTG. (R) For this project, the application targets Android only and uses the `usb_serial` Flutter package for USB CDC-ACM communication and the `sqflite` package for local SQLite storage. State management is handled by the Provider package. (I) The application exchanges newline-delimited JSON messages at 115,200 baud (8N1) with the Master. Incoming bytes are accumulated into a line-based parser that splits on the newline character (`0x0A`), and each complete JSON line is dispatched by event type: `ack` events update the device status model, `passenger` events create new log records in the local SQLite database, `dock` events update the dock state indicator, and `error` events surface diagnostic messages. The dashboard UI is designed with a premium dark-mode interface featuring a Master device status card, gradient-backed stat cards for today's revenue and passenger count, and a scrollable transaction feed. Application performance is validated by running a controlled set of boarding events and measuring the end-to-end USB-to-screen latency by comparing timestamps logged on both the Master serial monitor and the Flutter application.

# **3.6 Testing and Validation (Hardware Focus: Module & Power Testing)**

&emsp;&emsp;&emsp;This section describes the hardware verification test procedures used to validate the physical and electrical performance of the TOMS prototype. Each test is designed to produce quantitative, reproducible results using standard laboratory instruments.

## **3.6.1 PN532 I2C Bus Connectivity Test Procedure**

&emsp;&emsp;&emsp;(T) The first test verifies the physical and electrical integrity of the I2C communication interface between the ESP32-S3 microcontroller and the PN532 NFC transceiver on both Master and Slave platforms. (R) For this implementation, the I2C bus is configured at a fast-mode clock frequency of 400 kHz on GPIO 2 (SDA) and GPIO 3 (SCL), targeting the PN532 at I2C address `0x24`. (I) The test procedure is as follows: (1) power-cycle the device under test; (2) observe the serial monitor for the `pn532_init()` log output, which transmits a `GetFirmwareVersion` request frame and parses the response payload; (3) record whether the IC field reads `0x07` (PN532 chip identifier), the firmware major version reads `0x01`, and the minor revision reads `0x06`; (4) repeat for N consecutive cold-boot trials and compute the initialization success rate. Optionally, capture the I2C SDA and SCL waveforms on a digital storage oscilloscope to measure the 10%-to-90% rise time and verify signal integrity with the 4.7 kΩ pull-up resistors.

## **3.6.2 IRQ Latency Measurement Procedure**

&emsp;&emsp;&emsp;(T) The second test quantifies the response latency of the PN532's active-LOW interrupt (IRQ) line, validating the interrupt-driven design's superiority over continuous I2C polling. (R) For this design, the Master IRQ is mapped to GPIO 4 and the Slave IRQ is mapped to GPIO 5, both configured as falling-edge triggers using `GPIO_INTR_NEGEDGE`. (I) The test procedure uses a digital storage oscilloscope triggered on the IRQ falling edge: (1) bring an NFC target (the Slave) into the RF field of the Initiator (the Master); (2) measure the time from RF field activation to IRQ assertion across N tap events; (3) record the mean, standard deviation, and maximum latency; (4) establish a polling baseline by temporarily replacing the IRQ-driven code with a timed I2C register poll loop (e.g., 200 ms interval) and measuring the detection latency under the same conditions; (5) compute the latency reduction as `(1 − IRQ_mean / Poll_mean) × 100%`.

## **3.6.3 NFC-DEP Packet Delivery Reliability Test Procedure**

&emsp;&emsp;&emsp;(T) The third test validates the reliability and throughput of the NFC-DEP Peer-to-Peer communication link between the Master Initiator and Slave Target. (R) For this project, all tests are conducted at a baud rate of 424 kbps in passive mode, with the Master calling `InJumpForDEP` and the Slave responding via `TgInitAsTarget` with its 10-byte NFCID3 containing the hardware eFuse MAC address. (I) The test procedure is as follows: (1) write a test loop in the Master firmware that executes N sequential boarding transactions, each sending a 6-byte `toms_nfc_board_cmd_t` payload and waiting for a 1-byte `toms_nfc_ack_t` response; (2) hold the Master and Slave within 0–2 cm tap distance; (3) log `esp_timer_get_time()` before `InDataExchange` and after ACK received for each transaction to compute the round-trip time (RTT); (4) compute the packet success rate as `successes / N × 100%` and the mean RTT; (5) describe the cause of any failures observed (e.g., RF field loss, timeout).

## **3.6.4 Button Debouncing and State Machine Validation Procedure**

&emsp;&emsp;&emsp;(T) The fourth test validates the electrical operation, software debouncing, and UI state-machine transitions of the physical tactile push button on the Slave terminal. (R) For this terminal design, the button is connected to GPIO 4 in an active-low configuration with the ESP32-S3's internal pull-up resistor (`GPIO_PULLUP_ENABLE`) and an external 10 kΩ pull-up resistor. The firmware implements a 50-millisecond debounce timer for short presses and a 500-millisecond threshold for long presses. (I) The test procedure is as follows: (1) press the Slave button N times, divided between short presses (< 500 ms) and long presses (≥ 500 ms); (2) monitor the Master serial output for `BUTTON_PRESS` events received via ESP-NOW; (3) count false triggers, missed presses, and incorrect state transitions (e.g., a short press incorrectly triggering `TOMS_BTN_LONG_PRESS`); (4) compute the debounce accuracy rate; (5) optionally capture the button pin waveform on an oscilloscope to measure the mechanical bounce duration.

## **3.6.5 ADC Battery Monitoring Calibration Verification Procedure**

&emsp;&emsp;&emsp;(T) The fifth test verifies the calibration accuracy of the Analog-to-Digital Converter (ADC) circuit monitoring the Slave terminal's lithium-polymer battery voltage. (R) The ESP32-S3 Super Mini development board features an onboard TP4054 LiPo charging IC and a built-in resistor voltage divider (divider ratio 0.5) that scales the 3.0 V to 4.2 V battery voltage to a 1.5 V to 2.1 V range suitable for the ESP32-S3's internal ADC. The divided voltage is read by ADC1 Channel 0 (GPIO 1) configured with 12 dB attenuation. The calibrated output is computed using the ESP-IDF curve-fitting calibration API (`adc_cali_raw_to_voltage`), called by `toms_power_get_battery_mv()`. (I) The test procedure is as follows: (1) connect a bench power supply in place of the battery on the Slave's LiPo connector, set to a known reference voltage (e.g., 4,200 mV, 3,900 mV, 3,600 mV, 3,300 mV, 3,100 mV); (2) read the corresponding voltage from a calibrated digital multimeter (DMM) on the supply rail; (3) simultaneously read the firmware's `toms_power_get_battery_mv()` output via the serial monitor; (4) record both values and compute the discrepancy for each point; (5) repeat the full discharge cycle N times to verify that the firmware correctly triggers the low-battery warning at the 3,300 mV threshold and the critical shutdown at 3,100 mV.

## **3.6.6 Current Consumption and Battery Longevity Test Procedure**

&emsp;&emsp;&emsp;(T) The final test evaluates the current consumption profile of the Slave terminal across three distinct operational states and estimates the achievable battery longevity under a realistic duty cycle. (R) For this battery-powered terminal design, the ESP32-S3 Super Mini is powered by its onboard LiPo connector with a single-cell lithium-polymer battery. Current draw is measured using an inline digital ammeter (0.1 mA resolution) or an INA219 current sensor module placed in series with a fully charged lithium-polymer cell. The onboard TP4054 LiPo charging IC handles battery charging via USB-C. (I) The test procedure covers three states: (1) **Deep Sleep** — call `esp_deep_sleep_start()` and read the ammeter for the steady-state current; (2) **Active Idle** — run the Slave in normal operation (NFC Target listening active, LCD on, radio in standby, no active transaction) and read the ammeter; (3) **Peak Transaction** — initiate an NFC-DEP data exchange with simultaneous LCD redraw and ESP-NOW transmission and measure the peak current burst and its duration. Battery life is estimated as `capacity_mAh / measured_current_mA` for each steady-state mode. For the realistic duty cycle test, the Slave is fully charged, placed in Active Idle with periodic simulated boarding events (approximately one every 3–4 minutes to simulate ~200 events per shift), and the battery voltage is logged every 5 minutes until it reaches the 3,300 mV low-battery threshold. The total runtime in hours is recorded and compared against the target 12-hour operating shift.
