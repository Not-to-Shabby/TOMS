# Android gap check

Each claim from the review was checked against `origin/main` (7d81ab1) by reading the code. `./gradlew test` passes on that commit (debug and release). Nothing here was run on the phone, the Return Machine or the live server.

Verdicts: **confirmed**, **partly true**, **wrong**.

| # | Claim | Verdict | Evidence | Plan |
| --- | --- | --- | --- | --- |
| 1 | Sign-in is a stub; the shift screen returns to sign-in after a restart | **Partly true** | The backend has `POST /api/conductors/login` (`toms_backend/src/app.ts:142`, 16 h JWT, `auth.ts:15`). The app calls it (`RetrofitEventUploader.kt:229`, `ServerSessionRepository.login`). The stub (`StubSessionRepository`) is used only when `BuildConfig.TEST_FARES` is true and the server fails. What is true: the app **throws the token away** (`login` returns only the display name) and keeps the conductor only in `SessionUiState` (`SessionViewModel.kt:41`), which starts empty, so after a restart `MainActivity.kt:56` shows `LoginScreen` while the open shift survives in Room (`ShiftDao.open`). There is no sign-out button either. | Keep the token encrypted with `SecretCipher`, restore conductor and open shift on start, add sign-out that does not end the shift. No new endpoint is needed. |
| 2 | No foreground service, battery exemption, or kiosk | **Confirmed** | `AndroidManifest.xml` has no `<service>`, no `FOREGROUND_SERVICE*`, no `POST_NOTIFICATIONS`, no `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`. GPS (`LocationTracker`, collected by `ConductorViewModel.startLocation`) and the BLE link run only while the screen is in use. `UploadWorker` is a 15-minute periodic job plus a one-time kick (`UploadKick.kt`). Nothing keeps the process alive. | Foreground service started and stopped with the shift, one-time battery-exemption prompt, keep-screen-on setting. Kiosk stays a documented hook (MDM route is OPEN in `v2_decisions.md`). |
| 3 | No periodic status event | **Confirmed** | No `device_status` anywhere in `toms_android/app/src/main` or `toms_backend/src`. `dashboard.ts:295` has a comment "needs a heartbeat from the app (not built yet)". The Return Machine `heartbeat` in `RmProtocol.kt` is the RM's own telemetry, not the phone's. | `device_status` event, strict schema in ingest, migration. |
| 4 | Return Machine BLE only run against `FakeReturnMachineLink` | **Partly true** | The real client exists and is bound in DI: `AndroidBleReturnMachineLink` (383 lines), bound in `DataModule.kt:70`; the Fake is used only in tests. `RmProtocol.kt` UUID base and suffixes match `firmware/PROTOCOL.md` section 2 for the characteristics it uses (0x01 to 0x06, 0x09, 0x0A, 0x0E). What is true: no document in the repo records the app talking to a real Return Machine, and the unit tests use byte fixtures. `firmware-agent-brief.md` is not in the repo and `/mnt/project-files/` does not exist on this machine, so the comparison was made against `firmware/PROTOCOL.md` (v1.0) only. | Checklist only (`android_field_test_checklist.md`). No claim of a hardware pass. |
| 5 | WorkManager job and offline sync never observed on the phone | **Confirmed (in the repo)** | `v2_later.md` lists "Verify the WorkManager upload job on the phone: scheduled for every 15 minutes, never observed". `v2_progress.md` records no field run of offline sync. Unit tests cover the flusher and the kick (`OutboxTest`, `WorkManagerUploadKickTest`, `UplinkManagerTest`). | Checklist only. |
| 6 | No lost-card button, no late-payment screen, no shift history or export | **Confirmed** | `CardEvent.MARK_LOST` exists (`CardStateMachine.kt:15`) and is used nowhere in `ui/`. `fare_recovered` is accepted by ingest (`ingest.ts:200`) and the receipt (`receipt.ts:195`) but no phone code writes it. `ShiftEntity.summaryJson` is frozen at End Shift (`TripRepository.kt:186`) and `frozenSummary` reads one shift, but there is no list query or screen. | Build all three. The late-payment rule is **not decided**: `v2_decisions.md` says release is final and `v2_later.md` says it "needs a business decision on who may record it". I will not guess; see the PR description. |
| 7 | No direction check, stale fix while stopped, arbitrary 300 m cutoff | **Partly true** | Direction check: confirmed absent, already in `v2_later.md`. Stale fix: confirmed. `StopMatcher.DEFAULT_MAX_AGE_MILLIS` is 30 s and `LocationTracker.fixes` uses a 5 m update distance, so a stopped bus gets no new fix and `TripFactory` records no GPS (`TripFactory.kt:29`). **The 300 m cutoff is wrong for the current code**: `StopMatcher.nearest` uses each stop's own `radiusMeters`, default `DEFAULT_STOP_RADIUS_METERS = 100.0` (`Config.kt:9`), which matches the server default `radius_m` 100. The 300 m figure in `v2_later.md` is out of date. | Take one fresh fix at tap time when the last fix is stale. Update-distance stays. Name and comment the existing 100 m default (already a named constant) and correct `v2_later.md`. Direction check documented, not built. |
| 8 | SMS fallback, dual-SIM, authenticated cards deferred on purpose | **Confirmed** | `v2_later.md`: "Dual-SIM switching and encrypted SMS fallback" (design doc section) and "Authenticated cards". | Nothing to build. |
