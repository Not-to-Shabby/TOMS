# Return Machine — phone-side protocol note (conductor app)

What the conductor app implements of `firmware/PROTOCOL.md` (the firmware branch `v2/firmware-return-machine`, protocol v1.0), and what it deliberately does not. The firmware side is the source of truth; nothing here overrides it, and no hardware behaviour has been verified — see the firmware PR's own "not verified" list.

## What the phone implements now

| Area | Detail |
| --- | --- |
| Link | Central; scans for `TOMS-RM-*` / service `…4E45`; MTU 247; subscribes card_read (0x01), paid_check (0x03), heartbeat (0x05), rm_ack (0x0A), diag (0x0E); writes time_sync (0x06) on connect. |
| Paid check | `paid_check` → verdict reply on `paid_reply` (0x04) from the local card state machine: OK / UNPAID / UNKNOWN / ALREADY_RETURNED. |
| State table | `state_update` (0x02) snapshots on connect and deltas on every change; `rm_ack` (0x0A) is parsed. |
| Alarm | `diag 05 00` clears the held alarm (the machine holds it until this or the button). |
| **Read ack** (new) | After a card read is durably stored (the Room transaction over `rm_reads` and any machine-health events has committed), the phone writes `ack` (0x08) kind 2 with the **highest** stored read_seq. Never before the commit. A resent read is acked again without creating a second event. |
| **Signature verification** (new) | `card_read`, `heartbeat` and `rm_ack` notifies are framed (exact payload, or payload + 8-byte trailer) and the trailer is checked as HMAC-SHA256(key, suffix ‖ payload), first 8 bytes — the machine's own rule. With the key active, unsigned or badly signed notifies are dropped, counted and logged (reason + characteristic only, never the key or the bytes). Without a key, unsigned notifies pass and signed ones are dropped. The debug switch (`RmMachineTrust.allowUnverified`) can accept-and-count instead, and only exists in debug builds. |
| **Read de-duplication** (new) | Every read is stored under (machine id, read_seq) in the SQLCipher table `rm_reads` (Room schema 6); a resent read is a no-op insert, so a resend can never produce a second event. |
| **Machine-health events** (new) | `rm_stored_read` (one per read flushed from the machine's flash log — the phone was away when it was made), `rm_unverified` (the phone answered a paid check late or never, so the machine played the unverified tone), and `rm_lost_gap` (the previous read was of a lost card and the read_seq skips ahead: the machine's log overflowed). They upload through the outbox like any event and carry machine ids, sequence numbers and counts — **never passenger card UIDs**. |
| **Key enrolment** (new, see "Where the key comes from" below) | The server issues each machine's key; the enrolled phone for that vehicle fetches it over HTTPS with its device token, stores it Keystore-encrypted as *pending*, writes it with `diag 06` + 32 key bytes on the first bonded connection, and the key becomes *active* only when the machine's next signed message verifies. |
| **Wire layout 2** (new, opt-in) | After every connect and the time sync, the phone writes diag `07 02` and waits up to 3 s for the machine's `87 00 02 02`. On that reply the parser switches to layout 2 at once (on the Bluetooth callback thread, before the next notify is read); with no reply, or status 1/2, it stays on layout 1, byte for byte as before. The choice is per connection and is reset on every disconnect. Under layout 2 `card_read` has a trailing **outcome** byte (0 normal, 1 timeout, 2 no link; anything above 2 refuses the frame) and `heartbeat` has `dropped_reads` and `late_replies` (uint16 each); the trailer starts after them and still covers them. `paid_check` is expected before its `card_read` and is answered as always. |
| **Exact vs derived** (new) | On layout 2: `rm_unverified` comes from the outcome byte (`source: outcome`, reason `timeout` or `no_link`, no check number) and the phone's own paid-check timer is off so nothing is counted twice; `rm_lost_gap` comes from increases of `dropped_reads` (`source: counter`, `gap` = the increase; a value below the last one, such as a reset to zero, only moves the baseline); `rm_late_replies` comes from increases of `late_replies` (RAM only on the machine, restarts at a reboot). Baselines restart on each connect. On layout 1 the earlier inferences remain (`source: inferred` / `seq_jump`). The dashboard keeps exact and inferred counts in separate fields. |
| Heartbeat | Last heartbeat shown on More and the status strip; `buffered_reads` drives the stored-read labelling. |

## Known gaps (report, not fixed here)

- Layout 2 (outcome byte, `dropped_reads`, `late_replies`) is defined in section 7 of `firmware/PROTOCOL.md` on the firmware follow-up branch (draft PR #31), **not on `main`**. The phone side is built from that text and the firmware source only; it has not been run against a real machine. A machine that does not answer `07 02` keeps the older layout and the phone's inferences.
- **Signed writes, pairing and key replace follow `firmware/PROTOCOL.md` section 8 of the firmware hardening draft PR #35, which is not merged and not on `main`.** The phone is built from that text and its source only, so if #35 changes, this changes with it. Nothing here has run against a real machine. See "Writes, pairing and key replace" below.
- `device_info.valuesSigned` (flag bit 1) is decoded but not enforced; the gate's behaviour is driven by the stored key, which is the more direct source of truth.
- On the firmware that is on `main` today the key is **write-once** (`keystore_provision` returns `-EEXIST`, no replace command), so a rotation ends in the phone's "key mismatch" state with a plain message and a dashboard flag until the machine is updated or its key storage cleared. The replace flow below is for the firmware of draft PR #35, which adds diag `08`.
- A phone cannot choose the pairing method: Android picks it from what the phone can show and enter. The app watches what happened and tells the conductor; it cannot force numeric comparison. Whether Android's variant reports are reliable on the Tecno phone is untested.
- Recovery from a cleared bond (below) depends on `BluetoothDevice.removeBond`, which is a **system API, not part of the public SDK** (it is `@SystemApi` and `@hide` in the Android 13 source; the diagnostic app calls it by name for the same reason). It may be refused or missing on a given phone, and a later Android release may close it. The app handles that: it tells the conductor to forget the pairing in Bluetooth settings instead.

## Writes, pairing and key replace (firmware PR #35, section 8; phone side)

**Signed writes.** Once the machine has a key, the phone appends the usual 8-byte trailer (HMAC-SHA256(key, suffix || payload), first 8 bytes) to its writes, with the suffix of the characteristic it writes: `state_update` 02, `paid_reply` 04, `time_sync` 06, `ack` 08, and the diag characteristic 0E for `05`. `RmSignedWrites` builds all of them, for the real link and the fake. Only the **active** key signs, i.e. a key a message from the machine has already verified under; a pending key does not, and neither does a machine flagged as mismatched. The reason is that the machine refuses a **wrong** trailer on every write but accepts a missing one on the plain writes, so signing with a key the machine may not hold would turn working writes into refused ones.

**Clear alarm.** `05 00` plus the trailer over `0E || 05 00` (8.3). With no key anywhere it is sent as the two bytes it always was. Once the machine has a key the firmware accepts an unsigned `05` only under an interim rule (a bonded central with an open diagnostic session) that this app never meets, so signing is what keeps the button working. The button itself and its flow are unchanged.

**Pairing.** The machine pairs only in a 60 s window opened by holding its button at power-up, for one bond, and only with an authenticated pairing (8.1). The app calls `createBond()` as before; Android's public API gives the app no way to ask for numeric comparison or an authenticated bond, so what the app does is **watch and tell**: the pairing request's variant (numeric comparison and passkey are fine; anything else is reported), a bond that ends with no bond ("the Return Machine did not accept pairing", with the button steps, without claiming the window was closed since a cancel looks the same), and writes the machine refuses for lack of an authenticated link (ATT 5 and 15, or status 0xFF on a diag reply). The notice shows at the top of the Return Machine section on More.

**Key replace** (`RealRmProvisioner`). A key newer than the active one is sent with diag `08`: `08`, the 32 new key bytes, then the trailer over `0E || 08 || new key`, made with the key the machine holds (41 bytes, 8.4). The phone keeps signing with the old key until the first message verifies under the new one, which activates it (the machine keeps the old key for one step, so nothing stops in between). A lost reply is simply sent again. Outcomes: ok → written and waiting; no key on the machine → the new key goes with `06`; not signed under the current key → mismatch `machine_has_other_key`; a frame that is not a real status (an older firmware that does not know `08` echoes `88 <first key byte> 00 00`) → mismatch `rotation_needs_reflash`, **never read as success**; could not be saved or refused → the pending key is dropped and More says so in plain words; no answer → the pending key stays and the replace is sent again. No server change was needed (no new migration): the server already issues the new key and keeps the old one for a grace window, and the reasons it accepts are the ones the phone uses.

## A bond cleared on the machine (section 8.7)

Holding the button through the 5 s of the pairing window deletes the machine's bond and keeps its signing key. The machine then has no record of the phone, but **Android still holds the phone's half of the pairing**: the app only calls `createBond()` when Android says the machine is not bonded, so it never pairs again, and the machine refuses to encrypt ("PIN or key missing"), so each connection ends before it is usable. Without help that retries every few seconds, forever.

**What the phone does** (`RmPairingTracker`, `AndroidBleReturnMachineLink.forgetStalePairing`):
- It cannot read why a link dropped, so it counts the **signature**: a connection that came up (the machine answered) and ended before its notifications were on, while Android still reports the machine as bonded. A radio glitch does not count (one or two in a row), an attempt that never reaches the machine does not count, and a link that becomes usable resets the count. After 3 in a row (a matter of seconds, since the link retries every 3 s) the conductor is told.
- The prompt, on More, in plain words: the machine has forgotten this phone, tap **Forget old pairing**, then pair within 60 seconds of the machine showing PAIRING (hold its button while switching it on if not). There is also an **Open Bluetooth settings** button. The prompt is not wiped by the retries that follow it.
- **Forget old pairing** asks Android to remove the pairing and waits up to 15 s. If Android accepts, the tracker says the old pairing was removed and what to expect next (compare the number on the machine's screen; if nothing asks within a minute, hold the button while switching it on and try again). The next connection finds no bond, so the existing `createBond()` path pairs afresh. If Android refuses or the call is not available, the prompt says how to do it by hand (Bluetooth settings, TOMS-RM, Forget). A pairing removed by hand in Android settings is recognised the same way.
- **The key is not touched.** The machine kept it, and so did the phone, so after re-pairing signed notifies verify and signed writes are accepted again with no `06` or `08`. A pairing refused afterwards ends in the existing "did not accept pairing" notice.

**What it cannot tell:** whether a repeated failure is a cleared bond or something else that also ends links early (a flat machine, interference, another central holding the one connection). The prompt says what the phone sees, not why; the text is worded so that tapping "Forget old pairing" is harmless in any of those cases (the pairing is made again).

## Test evidence (host only — no hardware in the loop)

- `RmStaleBondTest` (21): the prompt only after three dropped attempts in a row with the bond held; not for a healthy link, for an out-of-range attempt, for no bond on the phone, for one attempt whose several steps fail, or for a weak pairing; it survives each retry; the removal, the follow-up notice, a pairing made afterwards, a pairing refused afterwards, Android refusing the removal, removal by hand, nothing to remove; the signing key and a signed Clear alarm afterwards; and no text names a command, a byte or a key. The tracker's calls are the very ones the real link makes, in the same order, through the fake link. The new tests were checked by breaking the code in several ways (including a prompt wiped by the next retry, a count that never resets, an attempt that never came up counted, and a usable link counted as failed); one of the first run's breaks survived and exposed a real gap (the per-attempt flag was not reset when a link ended), which is fixed and re-checked.

- `RmSecurityTest` (35): which key signs (active only; not pending, not mismatched; the old key through a replace), the exact bytes of each signed write and of `05` and `08` (suffix and signed region), each write judged by the fake's reading of section 8 (a wrong trailer refused, a missing one accepted and counted, unsigned `05` refused once a key exists), every pairing transition and the plain-words notices (with a check that no text names a command, byte or key), and the replace flow end to end (new key, lost reply and resend, other key on the machine, reset machine, older firmware echo for every possible first byte, each status, unauthenticated link, failure texts). The fake machine is a reading of the spec, not a machine. The new tests were checked by breaking the code in seven ways (never signing, never appending a trailer, a wrong suffix, a wrong command byte, a mismatched machine still signed for, an unrecognised reply read as success, Just Works accepted); every break fails a test.

- Trailer vectors were generated by compiling the firmware's own `sig.c` on a host with the firmware test's key and cross-checked against an independent HMAC implementation (`RmSignatureTest`).
- The framing, provisioning reply and decoders pass fuzz-style tests with random lengths and contents (`RmSignatureTest`).
- Layout 2: the section 7 byte examples (card_read `…01 02 01`, heartbeat with dropped `0x0102` / late `0x0304`) are test vectors, with signed lengths of 28 and 27 bytes, fuzzed for both layouts, plus the negotiation (write after connect, acknowledgement, silence, status 1/2, per-connection reset, the late and racing reply) in `RmLayoutV2Test`; outcome, counters, reboot resets and resent reads in `RmReadIntakeTest`. All against the fake link and the spec's bytes — not hardware.
- The verification gate, the intake (dedupe, ack-after-commit, stored-read events, gap events, late-reply events) and the trust store are covered in `RmNotifyGateTest` and `RmReadIntakeTest`, including a reconnect that resends 10 reads producing exactly 10 events and 10 acks.
- The Room 5→6 migration is validated against the exported schema in `MigrationTest`.

## Where the key comes from (Return Machine enrolment)

The server issues the key, so a replaced phone can fetch it again (a Keystore-bound key cannot be moved between phones).

1. **Registration.** An administrator registers a Return Machine on the dashboard (*Return Machines*: machine id and vehicle; one machine per vehicle). The server generates 32 random bytes from the OS CSPRNG and stores them **only** sealed with AES-256-GCM under `RM_KEY_MASTER_KEY`, binding the record id as additional authenticated data (a sealed key copied between rows does not open). Without the master key the routes answer 503 and nothing is stored or served. The key is never in a response to the dashboard, a log line, an audit row or a phone-uploaded event.
2. **Fetch.** `GET /api/device/return-machine-key` with the device token returns the key for **the machine of the vehicle the token's device is enrolled on** — the vehicle comes from the device record, never from a parameter. Another vehicle's phone, a phone with no vehicle, a revoked phone, a conductor or an admin token is refused. Rate-limited per phone (6 per minute, with `Retry-After`); the answer is `Cache-Control: no-store`. Every issue writes an `rm_key_issued` audit row (machine, key version, `device:<id>`; no key).
3. **Provision.** The phone stores the key as **pending** (`RmMachineTrust`, Keystore-bound `SecretCipher`) and writes it with `diag 06` over the bonded link. While a key is only pending the link keeps working: unsigned notifies still pass, and a signed one is checked against the pending key (and, in a rotation, the previous one).
4. **Activate.** The first signed message that verifies under the pending key activates it, drops the old key, and tells the server (`POST …/verified`, the loop closes and any mismatch flag for that key version clears). Retries with a capped, growing delay (15 s, 30 s, 1 min, 2 min, 5 min, then every 5 min) while the server or the machine does not answer; a machine that refuses or keeps another key is flagged once, not retried in a loop.
5. **Rotation.** An administrator rotates; the server keeps the previous key issuable for one hour (`GRACE_WINDOW_MS`, at most one old key). The phone fetches the new key, stores it pending (the old one still verifies), and re-provisions. **The firmware cannot take it** (write-once key, see "Known gaps"): the machine answers "already set", and the phone flags `rotation_needs_reflash` to the dashboard and to the conductor instead of retrying.
6. **Key mismatch** (a machine reset, a re-flash that kept the old key, or a machine provisioned from somewhere else): shown on the phone in plain words under the Return Machine facts on More, flagged on the dashboard with a bordered alert and an explanation, and written to the key audit trail (`rm_key_mismatch`). It clears when a message verifies under the current key version.

Nothing in this section was exercised against a real Return Machine. The key-handling code is covered by host-level tests (see the PR), and the diag `06` exchange is byte-level tested against the firmware's frames only.
